# D1: Grok Bot plugin-native distribution and host probe

## Goal

Make Grok Bot a verified, first-class install destination for cc/sp/kk by (1) probing a live Bot host to replace the unverified Sand/`update_state` assumptions behind ADR-036/037 with observed evidence, (2) emitting a Cursor-plugin bundle that Grok Bot installs through its documented plugin path, and (3) filtering or labeling skills whose runtime needs (local CLIs, hooks, subagents) a Bot cannot meet.

Evidence (checked 2026-11-04): Grok Bot "supports the same MCP servers, plugins, and skills as Cursor" (https://x.ai/bot/guides/grok-bot-101); Cursor loads Agent Plugins (root `plugin.json` + `skills/`) and Cursor Plugins (`.cursor-plugin/plugin.json`) (https://cursor.com/docs/plugins); Bots use up to 200 skills from installed plugins (Grok Bot changelog, Oct 2026). Tasks 0128/0130/0132 shipped with every live-host outcome UNVERIFIED and host smoke 0129 cancelled. Operator plan: individual (no Team Marketplace). Operator decision 2026-11-04: plugin emitter is Grok-Bot-only, no general `cursor` target.

## Scope

- **P0 probe:** read-only `cc-grok-bot-probe` skill the Bot reads-and-follows, emitting a sanitized JSON receipt (OS/arch, HOME, `SAND_*`, Sand/agent-data roots, skill-save tool name/schema, personal plugin install route from git URL or local dir, bun/CLI persistence across sleep/recreate, MCP-by-command). `superskill doctor --targets grok-bot` reads a supplied receipt and reports observed vs unverified capabilities.
- **P1 plugin emission:** `--materialize plugin` for the `grok-bot` target emits a Cursor-plugin bundle (`.cursor-plugin/plugin.json`, skills, commands→skills, agents→playbook skills, `mcp.json` with `${CURSOR_PLUGIN_ROOT}`) into an operator-chosen directory/git checkout; receipt + ownership markers as existing modes; 200-skill budget check; description lint. Existing `bridge`/`full` Sand modes stay as fallback. Mode becomes primary only when the P0 receipt confirms a personal install route.
- **P2 runtime requirements:** `requires:` frontmatter contract (`cli:<name>`, `hooks`, `subagents`, `local-fs`); grok-bot mapper excludes or labels "degraded" entities whose requirements the target cannot meet (probe-informed, overridable); cc plugin annotated.
- ADR-036/037 amendment and owning docs sync.

**Out of scope:** general `cursor` target, Team Marketplace automation, remote/SSH transport, automatic per-Bot enablement, a `superskill register` command, new dependencies.

## Acceptance Criteria

```gherkin
Feature: Grok Bot plugin-native distribution and host probe

  Scenario: R1 — Probe captures live host capability without mutation (R1)
    Given a Grok Bot told to read and follow the cc-grok-bot-probe SKILL.md
    When the probe runs
    Then it emits one sanitized JSON receipt with every capability marked observed, absent or unverified
    And it performs no writes outside its receipt file and exposes no secrets

  Scenario: R2 — Doctor reports probe evidence honestly (R2)
    Given valid, stale, malformed and missing probe receipts
    When superskill doctor --targets grok-bot runs in text and JSON modes
    Then observed capabilities are distinguished from unverified ones and existing exit semantics hold

  Scenario: R3 — Plugin mode emits an installable Cursor-plugin bundle (R3)
    Given the cc, sp and kk plugins
    When install runs with --targets grok-bot --materialize plugin
    Then a .cursor-plugin/plugin.json bundle with skills, adapted commands and playbook agents is written with receipt and ownership markers
    And reinstall, mode switch and prune keep unowned content untouched and failures restore prior output

  Scenario: R4 — Skill budget and descriptions are enforced (R4)
    Given a selection exceeding the 200-skill Bot cap or entities with missing or weak descriptions
    When plugin-mode install or dry-run runs
    Then the overflow and description findings are reported before any write and the install fails on cap overflow

  Scenario: R5 — Runtime requirements filter the Bot catalog (R5)
    Given entities declaring requires cli:spur, hooks or subagents
    When grok-bot install maps the catalog
    Then unmet entities are excluded or labeled degraded per the contract and other targets are unaffected

  Scenario: R6 — Documentation and gates (R6)
    Given the implemented probe, plugin mode and requires filter
    When ADR-036/037 and owning docs are synchronized and repository gates run
    Then every gate passes and live-host claims cite the probe receipt or remain marked unverified
```
