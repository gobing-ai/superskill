# B: Skills ecosystem compatibility (npx skills add interop)

## Goal
`superskill` consumes loose `SKILL.md` skills from the `npx skills` ecosystem (GitHub shorthand, URLs, local paths) and installs them with **uniform UX across every supported coding agent**, using the same per-target emission model as `superskill install`:

- **Tier 1 — universal agents** (read `.agents/skills` natively: codex, pi, omp, …): canonical copy at `<cwd|~>/.agents/skills/<sanitizeName(name)>`, no link needed.
- **Tier 2 — symlink-capable non-universal agents** (claude, opencode, antigravity-cli/ide, cursor, …): symlink from the agent's native skills dir to the canonical copy (the vendor's own model — `npx skills` interop preserved).
- **Tier 3 — translation-required agents** (no symlink support or divergent skill format, e.g. hermes/grok class, Windows junctions): transformed copy emitted by a per-target adapter that **reuses the `superskill install` emission machinery** (markdown transforms, reference rewriting) — no second translation convention.

Locks hash only the canonical untranslated copy, keeping hash-based `update` and `npx skills` round-trip interop intact.
## Scope
- In:
  - `superskill skill add|list|remove|update` verbs (source grammar, fetch, discovery, install, both lock files)
  - Three-tier per-target emission (canonical / symlink / translated-copy) covering all 9 superskill `Target`s
  - Per-target translation adapters reusing the `install` emission pipeline
  - Lock-schema interop with `npx skills` (project `skills-lock.json` v1, global `~/.agents/.skill-lock.json` v3)
  - Security parity (traversal guards, name/terminal sanitization, git transport hardening)
- Out:
  - `skill use` / `skill find` / well-known providers / `experimental_sync` (deferred)
  - Plugin install path changes (`superskill install` untouched)
  - Interactive prompt UI (CLI stays non-interactive, `--json` envelopes)
  - Content translation where a symlink already suffices (translation is minimal-by-design)

```gherkin
    And translation-required agents get a transformed copy via the install emission pipeline

  Scenario: Round-trip interop with npx skills
    Given a skill installed by "superskill skill add"
    When I run "npx skills list" and "npx skills remove <name>"
    Then the vendor CLI sees and removes the same install
    And vice versa for vendor-installed skills

  Scenario: Uniform UX across install surfaces
    Given an agent that cannot read ".agents/skills" or follow symlinks
    When I install a loose skill via "superskill skill add"
    Then the agent receives a working skill via translated copy
    And the observable result matches what "superskill install" delivers for plugin skills on that agent
```

- Surface decision (2026-07-24 brainstorm): new verbs under the existing `skill` noun group, NOT an overloaded `superskill install` and NOT a top-level `add`. Plugin `install` stays plugin-only.
- Port (not depend on) `vendors/skills` pure modules — vendor package has no exports map, is prompt/telemetry-coupled, and auto-wipes its global lock on version skew.

- Correctness invariant: locks hash the canonical untranslated copy only; translation is emission-layer, never lock-layer.
